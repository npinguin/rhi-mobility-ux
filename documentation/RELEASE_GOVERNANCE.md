# Release governance

RHI Mobility UX follows `documentation/UX_RELEASE_STANDARD.md`. This file adds Mobility-specific implementation rules.

## Canonical owners

| Concern | Owner |
| --- | --- |
| Package version | `package.json` |
| Mobility release context | `release/product.json` |
| Runtime version | generated by `tools/build.mjs` from `package.json` |
| Compatibility/publication metadata | generated/synchronized from the owners above |
| Test ownership | `tests/OWNERSHIP.json` |
| Runtime qualification | `release/QUALIFICATION.json` |
| Published candidate | immutable GitHub tag/release |

Do not copy the current version/backend baseline into additional governance checks or engineer notes as a second authority.

## Release path

```text
branch
→ PR
→ one full Validate gate
   → candidate build
   → owned test suites
   → deterministic rebuild proof
   → committed-dist equality
   → HACS validation
→ squash merge
→ Publish HACS verifies exact committed artifact
→ immutable HACS-visible TEST CANDIDATE
→ target HA qualification + rollback
→ manual stable promotion of exact immutable candidate
```

**Candidate publication does not rebuild. Stable promotion does not rebuild.**

## Test ownership

Testing follows the same ownership model as runtime code.

Normative sources:

- `documentation/TEST_GOVERNANCE.md`
- `tests/OWNERSHIP.json`
- `tools/check-test-ownership.mjs`

Rules:

1. one invariant has one test owner;
2. a test does not assert another owner's implementation details;
3. behavior is preferred over private implementation strings;
4. when several owners fail for one local change, investigate ownership drift before changing every test;
5. coverage may not be removed unless the owning test already proves the same invariant.

## Release identity

Run `npm run release:sync` when preparing a new candidate. It synchronizes the machine-readable compatibility/status identity from:

- `package.json`;
- `release/product.json`.

The human release notes and changelog remain required, but they describe the release rather than acting as machine authority.

## Published-version immutability

Published runtime bytes are immutable.

For a PR using an already published package version, Validate builds the branch and compares the generated JS/checksum with the published tag:

- identical runtime bytes → governance/test/documentation refactoring is allowed without fake version churn;
- different runtime bytes → the next package version is mandatory.

This replaces path-based immutability checks that incorrectly treated every source/test refactor as a runtime release.

## Build budget

Normal candidate: **2 builds total**.

- build 1: complete PR validation;
- build 2: deterministic reproducibility proof.

Main publication: **0 builds**.
Stable promotion: **0 builds**.

Any extra build is exceptional, not standard release procedure.

## Mobility boundaries

UX owns presentation only and consumes `MOBILITY_PUBLIC_RUNTIME_V1`. Backend semantics remain backend-owned.

Runtime controls remain fail-closed. Actual/readback remains operational truth. Global supervisor meaning remains backend-owned.

## Qualification

Static CI is not target Home Assistant evidence. `release/QUALIFICATION.json` qualifies the exact immutable candidate tag/SHA after publication.

Rollback remains a previous immutable HACS version.
